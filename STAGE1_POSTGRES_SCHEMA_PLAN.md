# Stage 1: Fresh PostgreSQL Schema and Data-Access Plan

## Planning boundary

This document proposes the initial schema and repository structure only. It does not apply migrations, connect to production, modify authentication, remove Supabase, or change customer-facing behavior. The schema is designed for an intentionally fresh PostgreSQL 18.4 database; no old Supabase data or `auth` schema is included.

## Design summary

- 40 application tables plus one migration-ledger table.
- UUID application keys generated by `gen_random_uuid()`; bigint identity only for high-volume append-only event/log tables.
- `timestamptz` for every timestamp.
- Integer/bigint minor units for all money.
- One canonical `users` identity shared by Credentials and Google.
- Auth.js JWT sessions initially, so there is no unused `sessions` table.
- `profiles.id` is a normal one-to-one FK to `users.id`; no `auth.users`.
- Existing API response shapes can be preserved with joins/views in repositories.
- Three unused historical affiliate tables are omitted from the initial schema and documented below.

## Complete table specification

Notation: `PK` primary key, `FK` foreign key, `UQ` unique, `NN` not null. All UUID PK defaults are `gen_random_uuid()` unless noted.

### Migration ledger

#### 1. `schema_migrations`

- Columns: `version text PK`, `checksum text NN`, `applied_at timestamptz NN default now()`, `execution_ms integer NN check >= 0`.
- Indexes: PK only.
- Purpose: immutable migration/checksum ledger. The runner also takes an advisory lock.

### Identity and profile

#### 2. `users`

- Columns: `id uuid PK`; `email text NN`; `normalized_email text NN`; `name text NN`; `password_hash text null`; `email_verified_at timestamptz null`; `image text null`; `role app_role NN default 'CUSTOMER'`; `status account_status NN default 'ACTIVE'`; `disabled boolean NN default false`; `must_change_password boolean NN default false`; `role_version integer NN default 1`; `session_version integer NN default 1`; `last_login_at timestamptz null`; `created_at timestamptz NN default now()`; `updated_at timestamptz NN default now()`.
- Constraints: UQ `normalized_email`; check `normalized_email = lower(btrim(email))`; check lengths for normalized email/name; check versions > 0; check `disabled = (status='DISABLED')` to avoid contradictory state.
- Indexes: unique `normalized_email`; `(role, created_at desc)`; `(status, created_at desc)`.
- Notes: only server code writes role; public signup always uses the database default CUSTOMER. `password_hash` is null for Google-only users.

#### 3. `accounts`

- Columns: `id uuid PK`; `user_id uuid NN FK -> users(id) on delete cascade`; `type text NN`; `provider text NN`; `provider_account_id text NN`; `created_at`, `updated_at timestamptz NN default now()`.
- Constraints: UQ `(provider, provider_account_id)`; UQ `(user_id, provider)` for one Google identity per user in the current provider set.
- Indexes: `(user_id)`; unique provider/account and user/provider indexes.
- Notes: provider access/refresh tokens are intentionally omitted because login does not call Google APIs. Credentials are represented by `users.password_hash`, not an `accounts` row.

#### 4. `profiles`

- Columns: `id uuid PK FK -> users(id) on delete cascade`; `phone text null`; `internal_notes text null`; `created_at`, `updated_at timestamptz NN default now()`.
- Constraints: PK/FK gives exactly zero or one profile per user; application transaction creates one for every user.
- Indexes: PK only; phone is not unique.
- Notes: name/email/image/role/status live only in `users`; repository joins preserve existing profile API shapes without duplicated authorization data.

#### 5. `auth_action_tokens`

- Columns: `id uuid PK`; `user_id uuid NN FK -> users(id) on delete cascade`; `purpose auth_token_purpose NN`; `token_hash text NN`; `expires_at timestamptz NN`; `consumed_at timestamptz null`; `attempt_count integer NN default 0`; `created_at timestamptz NN default now()`.
- Constraints: UQ `token_hash`; checks `attempt_count >= 0`, `expires_at > created_at`.
- Indexes: unique token hash; `(user_id, purpose, created_at desc)`; partial `(expires_at)` where `consumed_at is null`.
- Notes: stores only a cryptographic token hash. Creation invalidates prior unconsumed tokens of the same purpose in the same transaction.

#### 6. `auth_rate_limits`

- Columns: `action text NN`; `subject_hash text NN`; `window_started_at timestamptz NN`; `request_count integer NN default 1`; `blocked_until timestamptz null`; `expires_at timestamptz NN`; `updated_at timestamptz NN default now()`.
- PK: `(action, subject_hash, window_started_at)`.
- Constraints: count > 0; expiry after window start.
- Indexes: PK; `(expires_at)` for cleanup; partial `(blocked_until)` where not null.
- Notes: subject is a keyed hash of normalized email and/or client address, never a password/token.

### Products, orders, and payments

#### 7. `products`

- Columns: `id uuid PK`; `name text NN`; `slug text NN UQ`; `description text NN default ''`; `product_type product_type NN default 'OTHER'`; `sku text UQ null`; `price_minor integer NN`; `sale_price_minor integer null`; `currency text NN default 'INR'`; `stock integer NN default 0`; `low_stock_threshold integer NN default 5`; `images jsonb NN default '[]'`; `variants jsonb NN default '[]'`; `active boolean NN default true`; `featured boolean NN default false`; `archived_at timestamptz null`; `seo_title text null`; `seo_description text null`; `created_at timestamptz NN default now()`; `updated_at timestamptz NN default now()`.
- Checks: prices/stock/threshold >= 0; sale price >= 0; currency exactly 3 characters; JSON types are arrays.
- Indexes: unique slug/SKU; `(product_type, active)`; `(active, featured)`; `stock`; partial `(updated_at desc)` where not archived.

#### 8. `orders`

- Columns: `id uuid PK`; `order_number text NN UQ`; `customer_id uuid null FK -> users(id) on delete set null`; `customer_name text NN`; `customer_email text NN`; `customer_phone text null`; `status order_status NN default 'PENDING'`; `payment_status payment_status NN default 'PENDING'`; `currency text NN default 'INR'`; `subtotal_minor integer NN`; `discount_minor integer NN default 0`; `tax_minor integer NN default 0`; `shipping_minor integer NN default 0`; `total_minor integer NN`; `shipping_address jsonb NN default '{}'`; `billing_address jsonb NN default '{}'`; `courier text null`; `tracking_number text null`; `internal_notes text null`; `affiliate_id uuid null`; `affiliate_campaign_id uuid null`; `affiliate_source text null`; `affiliate_coupon_code text null`; `affiliate_code_snapshot text null`; `affiliate_attribution_method text null`; `affiliate_attributed_at timestamptz null`; `affiliate_commission_eligible boolean NN default false`; `affiliate_lead_id uuid null`; `created_at timestamptz NN default now()`; `updated_at timestamptz NN default now()`.
- FKs added after affiliate tables: `affiliate_id -> affiliate_profiles(id) on delete set null`; `affiliate_campaign_id -> affiliate_campaigns(id) on delete set null`; `affiliate_lead_id -> affiliate_business_leads(id) on delete set null`.
- Checks: all money >= 0; discount <= subtotal; total equals the chosen server formula; currency length 3; address values are objects.
- Indexes: unique order number; `created_at desc`; `(status, payment_status)`; `(customer_id, created_at desc)`; `(affiliate_id, created_at desc)`; `(payment_status, created_at desc)`.
- Delete behavior: deleting a user never deletes financial history; customer snapshots remain.

#### 9. `order_items`

- Columns: `id uuid PK`; `order_id uuid NN FK -> orders(id) on delete cascade`; `product_id uuid null FK -> products(id) on delete restrict`; `product_name text NN`; `product_type product_type NN`; `sku text null`; `variant jsonb NN default '{}'`; `quantity integer NN`; `unit_price_minor integer NN`; `total_minor integer generated always as (quantity * unit_price_minor) stored`.
- Checks: quantity > 0; unit price >= 0; variant is object.
- Indexes: `(order_id)`; `(product_id)`.

#### 10. `payments`

- Columns: `id uuid PK`; `order_id uuid NN FK -> orders(id) on delete restrict`; `provider text NN`; `provider_transaction_id text NN`; `idempotency_key text NN`; `amount_minor integer NN`; `currency text NN`; `status payment_status NN default 'PENDING'`; `failure_reason text null`; `refunded_minor integer NN default 0`; `provider_created_at timestamptz null`; `created_at timestamptz NN default now()`; `updated_at timestamptz NN default now()`.
- Constraints: UQ `(provider, provider_transaction_id)`; UQ `(provider, idempotency_key)`; amount >= 0; refund between 0 and amount; currency length 3.
- Indexes: unique provider transaction/idempotency; `(order_id)`; `(status, created_at desc)`.

#### 11. `payment_webhook_events`

- Columns: `id uuid PK`; `payment_id uuid null FK -> payments(id) on delete restrict`; `provider text NN`; `provider_event_id text NN`; `provider_transaction_id text null`; `payload_hash text NN`; `signature_verified boolean NN default false`; `status webhook_processing_status NN default 'RECEIVED'`; `attempt_count integer NN default 0`; `last_error text null`; `received_at timestamptz NN default now()`; `processed_at timestamptz null`; `updated_at timestamptz NN default now()`.
- Constraints: UQ `(provider, provider_event_id)`; count >= 0; processed timestamp required when status is PROCESSED.
- Indexes: unique provider event; `(payment_id)`; `(provider, provider_transaction_id)`; `(status, received_at)`.
- Notes: stores no full sensitive payload by default. Verified processing and payment/order updates happen atomically.

### Physical and digital cards

#### 18. `digital_cards`

- Columns: `id uuid PK`; `owner_id uuid NN FK -> users(id) on delete restrict`; `slug text NN UQ`; `profile jsonb NN default '{}'`; `design jsonb NN default '{}'`; `active boolean NN default false`; `activated_at timestamptz null`; `expires_at timestamptz null`; `created_at timestamptz NN default now()`; `updated_at timestamptz NN default now()`.
- Checks: slug regex `^[a-z0-9][a-z0-9-]{2,79}$`; JSON objects; expiry after activation when both present.
- Indexes: unique slug; `(owner_id, updated_at desc)`; partial `(slug)` where active.
- Change from old schema: activation secret is moved out; user deletion is restricted while cards exist.

#### 19. `cards`

- Columns: `id uuid PK`; `owner_id uuid null FK -> users(id) on delete restrict`; `digital_card_id uuid null UQ FK -> digital_cards(id) on delete set null`; `public_token text NN UQ`; `inventory_reference text UQ null`; `status card_status NN default 'UNASSIGNED'`; `replacement_card_id uuid null FK -> cards(id) on delete set null`; `assigned_at timestamptz null`; `programmed_at timestamptz null`; `tested_at timestamptz null`; `shipped_at timestamptz null`; `activated_at timestamptz null`; `created_at timestamptz NN default now()`; `updated_at timestamptz NN default now()`.

- Indexes: unique public token/inventory/digital-card; `(owner_id, created_at desc)`; `(status, updated_at desc)`; `(replacement_card_id)`.
- Notes: tokens come from a cryptographically secure 128-bit-or-greater random source and are never sequential.

## Existing routes that will need later changes

Stage 1 itself changes none. Eventual direct-PostgreSQL changes are required in every currently Supabase-backed route:

- Auth: `signup`, `login`, `logout`, `me`, `refresh`, `forgot-password`, `reset-password`, `change-password`, `resend-confirmation`, `[...nextauth]`.
- Admin: `admins`, `audit`, `dashboard`, `customers`, `customers/[id]`, `customers/reset`, `products`, `orders`, `payments`, `settings`, `notifications`, `support`, `cards/activation`, and all six `admin/affiliates/*` areas.
- Affiliate: `apply`, `campaigns`, `dashboard`, `export`, `leads`, `payouts`, `qr`, plus commission cron.
- Commerce/customer/public: `checkout`, `orders`, invoice, Razorpay verify/webhook, cards CRUD/activate/public/lead, `support`, `media`, product detail.
- Shared/page code: `adminAuth.ts`, `auth.ts`, `affiliate.ts`, affiliate/order notification helpers, `middleware.ts`, affiliate terms page, and product detail page.

The route inventory currently contains 49 route files; routes without direct Supabase calls still require review if their identity comes from `currentIdentity()`.

## Tables intentionally omitted as unnecessary initially

1. `sessions`: Auth.js JWT strategy does not use it. Add later only if individual server-side session listing/revocation is required.
2. `verification_tokens` in Auth.js adapter form: purpose-specific `auth_action_tokens` covers verification/reset with hashing, consumption and attempts.
3. Historical `affiliate_attributions`: no current route reads/writes it; the application snapshots validated attribution on `orders`. Reintroduce only if pre-conversion attribution history becomes a product requirement.
4. Historical `affiliate_coupons`: no current route reads/writes it; current behavior uses unique `affiliate_profiles.coupon_code` and settings. Add a dedicated table later only for multiple coupons, validity windows or campaign-specific discounts.
5. Historical `affiliate_tier_history`: no current route reads/writes it. Tier changes must still create `admin_audit_logs`; add the table if product reporting needs a first-class history timeline.
6. Separate `admins` table: roles belong to canonical users. A second admin identity store would create authorization drift.
7. Generic `events`/`analytics` table: existing card and affiliate event tables have clearer retention, privacy and indexes.
8. Blob/media table: PostgreSQL should store URLs/metadata, not uploaded binaries. Object storage remains a separate decision.

## Missing tables/features discovered

- Canonical `users` and provider `accounts` do not exist in the old schema.
- Secure hashed email-verification/password-reset token storage is missing because Supabase previously supplied it.
- Distributed login/signup/reset rate-limit persistence is missing.
- Physical NFC inventory/lifecycle and one-time activation records are missing; `digital_cards` alone cannot model UNASSIGNED through LOST/REPLACED.
- Durable payment webhook idempotency/processing records are missing.
- Session-wide revocation is missing; `users.session_version` supplies it for JWT sessions.
- Media/object storage remains unresolved once Supabase Storage is removed; this needs a separate design before Stage 5/6.
- Email delivery infrastructure for verification/reset must be selected/verified; existing notification mail code is not automatically an auth mailer.
- Retention/cleanup jobs are needed for expired auth tokens/rate limits and privacy-sensitive event hashes.
- Database backup, migration status, health check, least-privilege application role, and restore rehearsal procedures must be defined for deployment.

## Approval questions for Stage 1 implementation

Approval should explicitly cover:

1. The 40-table application set and the eight unnecessary-table categories omitted above (including three historical affiliate tables).
2. JWT sessions without a sessions table.
3. `profiles.id = users.id` one-to-one, with authorization fields only in users.
4. Separate `cards` and `card_activations` alongside `digital_cards`.
5. Versioned raw SQL plus the `pg` migration runner.
6. Reference defaults only; no user/admin/customer/business seed data.

After approval, Stage 1 implementation should add only the database layer, reproducible migrations, repository modules, and their tests. It should still not change authentication routes or apply SQL to production.
